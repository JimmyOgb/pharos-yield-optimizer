## 1. Executive Summary

This audit assesses the end-to-end consistency between the recommendations generated by `recommendationEngine.ts` and the transaction calldata produced by `transactionReviewer.ts`.

### Key Findings:
1. **Protocol Compatibility:** **COMPATIBLE.** Both modules target the exact same canonical Faroo stPROS proxy contract (`0x6b0A44c64190279f7034b77c13a566E914FE5Ec4`), and the stPROS shares minted by the reviewer's deposit call are fully compatible with the protocol's 14-day unbonding queue.
2. **Deposit Path Assumption Mismatch:** **INCONSISTENT IN GAS ALLOCATION.** The recommendation engine evaluates entry using a 115,000 gas abstraction (`FAROO_DEPOSIT_SUBMIT`), while the transaction reviewer generates calldata for a 3-step sequence using 180,000 gas (Wrap 45k + Approve 45k + Deposit 90k).
3. **Failsafe Integrity:** **VERIFIED SECURE.** Disqualified assets (Axil Prime Credit, Native PoS Consensus) strictly return `UNAVAILABLE` and cannot produce transaction calldata. Malformed or stale inputs trigger `STAY_PUT` or `INSUFFICIENT_DATA`.

## 2. Granular Consistency Verification

### 2.1 Does the Recommendation's Assumed Deposit Path Match the Reviewer?
- **Protocol Contract Match:** **YES.** Both interact with Faroo Liquid Staking stPROS (`CANONICAL_CONTRACTS.FAROO_STPROS`).
- **Underlying Asset Match:** **YES.** Both recognize WPROS (`CANONICAL_CONTRACTS.CANONICAL_WPROS`) as the underlying asset for Faroo staking.
- **Gas Model Match:** **NO (PARTIAL MISMATCH).**
  - In [`src/engine/frictionModel.ts`](file:///C:/Users/NO%20GO%20NO/PharosBuild/skills/pharos-yield-optimizer/src/engine/frictionModel.ts#L18): Entry is modeled as a single deposit submit call of `115,000 gas`.
  - In [`src/reviewer/transactionReviewer.ts`](file:///C:/Users/NO%20GO%20NO/PharosBuild/skills/pharos-yield-optimizer/src/reviewer/transactionReviewer.ts#L130): Entry is constructed as 3 discrete EVM calls: `deposit()` on WPROS (45k) + `approve()` on WPROS (45k) + `deposit(assets, receiver)` on Faroo vault (90k) = `180,000 gas`.
  - **Audit Finding:** The reviewer prepares calldata for native PROS holders requiring wrapping and approval, whereas the recommendation engine models a direct deposit benchmark.

### 2.2 Is the Exit Method Compatible with the Selected Deposit Position?
- **Yes.** Calling `deposit(amountWei, userAddress)` on `0x6b0A44c64190279f7034b77c13a566E914FE5Ec4` mints `stPROS` shares to the user's wallet.
- The `stPROS` token is the sole input accepted by Faroo's `requestWithdraw` unbonding queue.
- Therefore, the position minted during entry is 100% compatible with the 14-day unbonding queue exit assumed by the recommendation engine.

### 2.3 Does the Friction Calculation Include Correct Entry and Exit Operations?
- **In `frictionModel.ts` (`faroo-patient-staking`):**
  - Includes Entry (`115,000 gas`)
  - Includes Exit (`85,000 gas`)
  - Total gas charged: `200,000 gas units`
  - Fees: 0% mint fee + 0% queue exit fee
- **If evaluated against the 3-Step physical entry path:**
  - True physical entry gas: `180,000 gas`
  - True physical exit queue gas: `85,000 gas`
  - True physical lifecycle: `265,000 gas units`
  - The recommendation engine charges `200,000 gas`, which understates physical lifecycle gas by `65,000 gas units` ($0.00008125\text{ PROS}$ at 1.25 Gwei).

## 3. Disqualification and Failsafe Verification

### 3.1 Can an Unavailable Strategy Silently Become a Valid Recommendation?
- **NO.**
- In `recommendationEngine.ts` lines 201-208:
  - `native-pros-baseline` is excluded as a yield destination.
  - `axil-prime-credit-3m` is strictly filtered out of automated PROS rebalancing (`if (c.profile.id === 'axil-prime-credit-3m') return false`).
  - Strategies with lockup periods exceeding `horizonDays` are strictly filtered out (`if (!c.isLockupEligible) return false`).
- In `transactionReviewer.ts` lines 284-330:
  - Axil Prime Credit returns `payloadStatus: 'UNAVAILABLE'` with an explicit error message: `TRANSACTION_PAYLOAD_UNAVAILABLE`.
  - Native PoS Consensus returns `payloadStatus: 'UNAVAILABLE'`.

### 3.2 Safety of `STAY_PUT` and `INSUFFICIENT_DATA` Failsafes
- Zero principal input $\to$ returns `STAY_PUT` (`ZERO_PRINCIPAL_INPUT`).
- Horizon shorter than lockup (e.g. 7 days vs 14 days) $\to$ returns `STAY_PUT` (`HORIZON_SHORTER_THAN_LOCKUP`).
- Friction exceeds yield (e.g. 1-day horizon with DEX exit) $\to$ returns `STAY_PUT` (`FRICTION_EXCEEDS_GROSS_YIELD`).
- Stale or unavailable on-chain RPC $\to$ returns `INSUFFICIENT_DATA` (`STALE_OR_MISSING_ONCHAIN_DATA`).
- In all negative cases:
  - `netAdvantageWei` is forced to `0n`.
  - The UI disables the "Review Transactions" button (`openReviewerBtn.disabled = true`), preventing any transaction calldata from being exposed.

## 4. Identification of Missing Evidence

To achieve 100% mathematical closure between `frictionModel.ts` and `transactionReviewer.ts`, the following protocol evidence is currently missing from the codebase:

1. **Existence of a Single-Tx Native Deposit Helper:**
   - Does Faroo have a deployed peripheral contract (e.g. `FarooNativeStaker` or payable `submit()`) on Pacific Mainnet that wraps native PROS and mints stPROS in a single transaction?
   - If YES: Its contract address, verified ABI, and selector are missing from `CANONICAL_CONTRACTS` and `transactionReviewer.ts`.
   - If NO: The `FAROO_DEPOSIT_SUBMIT: 115_000n` benchmark in `frictionModel.ts` is an outdated abstraction, and `frictionModel.ts` should be updated to charge the full 3-step ERC-4626 entry sequence (`180,000 gas`) instead of `115,000 gas`.
2. **On-Chain Gas Receipt for `requestWithdraw`:**
   - The `85,000 gas` allocation for `FAROO_REQUEST_WITHDRAW` is a forward empirical estimate, not a verified transaction receipt.
   - However, 85,000 gas is typical and conservative for an ERC-7540 queue insertion.
